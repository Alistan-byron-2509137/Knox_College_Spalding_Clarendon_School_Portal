How to use this guide

The assignment gives each group 20 minutes: a 10-minute presentation (20 marks) and a 10-minute viva (30 marks, questions about the source code based on Bloom’s Taxonomy). The presentation marks look at a working application with no console errors and at the design and navigation. The viva checks that you understand your own code.

Study the code, not only this guide. The viva questions are about the files you submit. Before the day, open each file once and read it slowly, using Part C as a map. Every code box in this guide is copied from your real files. If your course requires you to declare help from AI tools, check with Miss Anuli and declare it.

Part A is the presentation plan. Part B is a one-page checklist for the day. Part C is the viva study guide, written in simple language.

C2. HTML

  • Semantic elements describe the meaning of each area: header, nav, main, section, article, aside (dashboard menu), footer, address, table with caption, thead, tbody, and th scope="col". Screen readers and search engines use them.
  • Forms: every input has a label linked with for and id. The Contact form uses HTML5 rules: required, type="email", pattern (a regular expression), minlength, maxlength, and title (the hint text).
  • Accessibility touches: a skip link, aria-current="page" on the current menu link, aria-expanded on the phone menu button, visible focus outlines, and alt text on images.
  • Why the same header in each page? Each page repeats the same header and footer HTML, and JavaScript adds the Login or Logout links, so the menu always matches the login state.

C3. CSS

  • CSS variables (:root) hold the school colours, so changing --blue or --red changes the whole site.
  • Flexbox (one direction): the header, button rows, toolbars. Grid (rows and columns): card grids, forms (repeat(auto-fit, minmax(...))) and the dashboard (230px menu + content).
  • Media queries at 900px (dashboard menu goes on top), 768px (header menu becomes a button) and 480px (smaller headings, full-width buttons). @media print hides the menu and footer so only the report card prints.
  • Tables sit inside .table-wrap with overflow-x: auto, so a wide table scrolls inside its box instead of breaking the page on a phone.
  • The guard class: dashboards start with body.guard main { visibility: hidden; }. JavaScript removes the class only if the login check passes, so nothing flashes on screen for the wrong person.

C4. JavaScript basics used

  • Variables: const for values that are not reassigned, let for values that change (counters, totals). No var.
  • Arrays and objects: a student is an object ({ id, firstName, ... }); the list of students is an array of those objects.
  • Functions: each function does one job (for example getFinance works out money). Some functions return a value, others change the page.
  • Loops and conditions: for...of loops go through records; if / else if / else decides statuses, letter grades and validation.
  • Events: addEventListener("click", ...), "submit", "input", "change". event.preventDefault() stops the browser from reloading the page when a form is submitted.
  • DOM: getElementById finds an element; createElement, appendChild and textContent build tables and messages.
  • textContent, not innerHTML: text typed by a user is shown with textContent, so it can never run as code. That protects against XSS (cross-site scripting). My lecture notes warn about innerHTML with user input.

C5. Browser storage (the simulated database)

  • localStorage keeps text under a key, stays after the tab or browser closes, and is shared by all pages of the same website address. sessionStorage works the same way but is cleared when the tab closes. I use localStorage for records and sessionStorage for the login.
  • Storage only holds text, so lists of objects are turned into text with JSON.stringify and back with JSON.parse.
  • Limits: about 5 MB per site, only in that browser, anyone can read or change it with the developer tools, and it is not a real database.
function loadList(key) {
  const text = localStorage.getItem(key);
  if (text === null) {
    return [];
  }
  try {
    const data = JSON.parse(text);
    if (Array.isArray(data)) {
      return data;
    }
    return [];
  } catch (error) {
    return [];
  }
}
function saveList(key, list) {
  localStorage.setItem(key, JSON.stringify(list));
}

Explain it: loadList reads the text. If nothing is saved (null) or the text is damaged (the catch), it returns an empty list so the page does not crash. saveList turns the list into text and stores it. Every other function in the project reads and writes through these two. That is how pages share data and how records survive a refresh.

First visit: initData() checks the key knox_data_ready. If it is missing, seedAllData() saves the sample users, teachers, subjects, classes, students, payments, grades and announcements.

function deleteStudent(id) {
  const student = getStudent(id);
  if (student === null) {
    return;
  }
  const sure = confirm("Delete " + fullName(student) + " (" + id + ")? Their grades and payments will also be deleted.");
  if (!sure) {
    return;
  }
  saveList(KEYS.students, loadList(KEYS.students).filter(function (item) {
    return item.id !== id;
  }));
  saveList(KEYS.grades, loadList(KEYS.grades).filter(function (item) {
    return item.studentId !== id;
  }));
  saveList(KEYS.payments, loadList(KEYS.payments).filter(function (item) {
    return item.studentId !== id;
  }));
  if (editingId === id) {
    resetStudentForm();
  }
  document.getElementById("studentProfile").hidden = true;
  showMessage(document.getElementById("studentMessage"), "Student " + id + " was deleted.", "success");
  refreshAfterStudentChange();
}

Explain it: filter keeps every record whose ID is not the deleted one. It is done three times (students, grades, payments) so no orphan records are left behind.

function changeStudentIdEverywhere(oldId, newId) {
  const grades = loadList(KEYS.grades);
  for (const grade of grades) {
    if (grade.studentId === oldId) {
      grade.studentId = newId;
    }
  }
  saveList(KEYS.grades, grades);

  const payments = loadList(KEYS.payments);
  for (const payment of payments) {
    if (payment.studentId === oldId) {
      payment.studentId = newId;
    }
  }
  saveList(KEYS.payments, payments);
}

Validation and duplicate IDs

  • The ID must match ^KC\d{5}$: “KC” and exactly five digits.
  • Duplicate check: students.some(student => student.id === id && student.id !== editingId). The and not editingId part lets a student keep their own ID while editing.
  • Names must be letters (2 to 40), the date of birth must give an age from 10 to 21, the phone must have 10 digits, the email is optional but must be valid if typed, and tuition must be a number that is 0 or more.
  • All problems are collected in an array and shown together in a list, so the Administrator sees everything to fix at once.
  • Missing data: if a list is empty the table shows a friendly row (“No students match your search”), and a blank mark is allowed and shown as “-”.

C7. Authentication (simulated)

function loginUser(username, password) {
  const users = loadList(KEYS.users);
  for (const user of users) {
    if (user.username === username && user.password === password) {
      const session = {
        username: user.username,
        role: user.role,
        name: user.name,
        teacherId: user.teacherId
      };
      sessionStorage.setItem(KEYS.session, JSON.stringify(session));
      return user;
    }
  }
  return null;
}
function requireRole(role) {
  const session = getSession();
  if (session === null) {
    window.location.href = "login.html?msg=login";
    return null;
  }
  if (session.role !== role) {
    window.location.href = "login.html?msg=denied";
    return null;
  }
  // The page starts hidden (class "guard"). Show it now that access is OK.
  document.body.classList.remove("guard");
  return session;
}

Explain it: loginUser compares the typed username and password with the saved accounts. On a match it saves a small session note (username, role, name) in sessionStorage. login.js then sends the person to dashboardPageFor(role). At the top of every dashboard script, requireRole sends people away if there is no session or the role is wrong, and only then removes the guard class. Logout deletes the session note and returns to the login page.

Limits (very likely viva question)

  • Passwords are plain text in localStorage. Anyone can open DevTools > Application and read them.
  • The role check lives in the browser. A person could edit the stored session to say “admin”.
  • No hashing, no lock-out, no HTTPS, no real session token or expiry.
  • Better design: send the password to a server over HTTPS, store only a salted hash, give the browser a token, and let the server decide what each role may see or change.

C8. Calculations (with worked examples)

Grades

function subjectAverage(record) {
  if (record === null) {
    return null;
  }
  const marks = [];
  const values = [record.test1, record.test2, record.exam];
  for (const value of values) {
    if (value !== null && value !== undefined && value !== "") {
      marks.push(Number(value));
    }
  }
  if (marks.length === 0) {
    return null;
  }
  let total = 0;
  for (const mark of marks) {
    total += mark;
  }
  return Math.round((total / marks.length) * 10) / 10;
}
function letterGrade(average) {
  if (average === null) {
    return "N/A";
  }
  if (average >= 80) {
    return "A";
  }
  if (average >= 70) {
    return "B";
  }
  if (average >= 60) {
    return "C";
  }
  if (average >= 50) {
    return "D";
  }
  if (average >= 40) {
    return "E";
  }
  return "F";
}
function parseScore(text) {
  const clean = String(text).trim();
  if (clean === "") {
    return { ok: true, value: null };
  }
  const number = Number(clean);
  if (Number.isNaN(number) || number < 0 || number > 100) {
    return { ok: false, value: null };
  }
  return { ok: true, value: number };
}

Tuition

function getFinance(student) {
  const payments = getPaymentsFor(student.id);
  let paid = 0;
  for (const payment of payments) {
    paid += Number(payment.amount);
  }
  const due = Number(student.tuitionDue) || 0;
  const balance = Math.max(Math.round((due - paid) * 100) / 100, 0);

  let status = "Pending";
  if (balance <= 0) {
    status = "Paid";
  } else if (student.dueDate && todayISO() > student.dueDate) {
    status = "Outstanding";
  }
  return { due: due, paid: paid, balance: balance, status: status, payments: payments };
}

Explain it: add up all payments for the student, subtract from the tuition due (never below zero), then decide the status with if / else if. Math.round(x * 100) / 100 avoids tiny decimal errors with money. Dates written as YYYY-MM-DD can be compared as text, so todayISO() > dueDate works.

C11. How to answer in the viva

  • Answer the question you were asked first, in one or two sentences, then add an example from your code.
  • Name the file and function (“in shared.js, the function getFinance”). Examiners like specific answers.
  • If you do not know, say what you do know and how you would find out (for example, check the lecture notes or MDN). Do not guess wildly.
  • Be honest about limits. Saying “this login is only a simulation and here is how a real one works” scores better than defending it.
  • Practise by opening a file, picking any function, and explaining it out loud in 30 seconds.
